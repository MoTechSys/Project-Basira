# Integrations — what exists, what the strong Islamic platforms do, what Basira should add

Status: **survey + design (2026-10-01)**. Nothing in §3 is implemented yet; §1 is live. Every external claim below was read from the linked page on 2026-10-01 — not from memory.

## 1. What Basira exposes today (live, verified against `/openapi.json`)

| Surface | Path | Notes |
|---|---|---|
| OpenAPI 3.1 document | `GET /openapi.json` | generated by FastAPI; title «Basira API», version `0.1.0` |
| Interactive docs (Swagger UI) | `GET /docs` | on unless `BASIRA_DOCS=0`; ReDoc disabled |
| Health gate | `GET /health` | 503 with error envelope until index loaded; counts, rss, build sha, provider names |
| Check text | `POST /v1/check` | `{text ≤ 5000, ui_lang, source_modality, options}` → `CheckResponse` |
| Check image | `POST /v1/check/image` | multipart `image` (+ `ui_lang`); returns `ocr_text` so the user can verify what was read (ADR-003) |
| Sources manifest | `GET /v1/sources` | name, version/commit, licence + URL, record count |
| Message catalogue | `GET /v1/messages/{ar\|en}` | single source of all user-facing strings |

Guards: CORS allow-list, rate limit 30/min per client (`X-Eval-Key` bypass), error envelope `{error:{code,message_ar,message_en}}`, class-only logging, no persistence.

Frontend footer already links to `/docs` (Vite proxies `/docs` and `/openapi.json` to :8000). **Production needs the same reverse-proxy rule** (WP-10).

## 2. Survey — strong Islamic platforms, developer surfaces (read 2026-10-01)

| Platform | What they offer developers | What is worth adopting | What we must NOT copy |
|---|---|---|---|
| **Quran Foundation / quran.com** — api-docs.quran.foundation | Developer Console (app registration), Content APIs `GET /content/api/v4/…` with OAuth2 client-credentials, official JS/TS SDK (`@quranjs/api`) and Python SDK (`quran-foundation-api` on PyPI), User APIs (bookmarks…) behind OIDC | Clear *two-tier* docs: «Quickstart in 5 minutes» + reference generated from the OpenAPI spec; typed SDK as the first-class path | User accounts / OAuth — Basira stores nothing, so there is no user data to protect; adding login would contradict SAFETY |
| **quran/quran-mcp** (github.com/quran/quran-mcp, remote `https://mcp.quran.ai`) | Remote **streamable-HTTP MCP server**; tools `fetch_quran`, `search_tafsir`, …; MCP *resources* and *prompts*; a middleware layer for **rate limiting, grounding, logging**; one-line client config for Claude Desktop / ChatGPT | Remote-first MCP (no install), a *grounding* middleware that tells the model how to cite, and a documentation site served by the same process | Tafsir/translation tools — out of scope and would require us to serve interpretive text |
| **hadith-mcp.org** | Six read-only tools incl. **`fetch_grounding_rules`** (returned once per session: citation rules + limitations), `fetch_hadith`, `search_hadith`, `fetch_cross_references`, `show_hadith` (MCP app UI); a companion web app «verify AI citations quickly» with **shareable proof links**; explicit disclaimer that provenance tags are heuristics, not rulings | `fetch_grounding_rules` pattern (we have the equivalent text in SAFETY §1.3 and `transparency_notice`); shareable, stateless proof links; the honesty of labelling algorithmic output as algorithmic | Semantic (embedding) search as a *verification* primitive — non-deterministic; our matching stays deterministic (I1–I9) |
| **sunnah.com** — sunnah.com/developers | REST API documented on Stoplight; **API key by GitHub issue**; community reports slow/unanswered key requests (reddit, issue #2849, 2026-03) | Public OpenAPI reference | Gate-kept keys — Basira's check endpoint is public with rate limiting; eval key is for benchmarks only |
| **dorar.net** — article 389 «خدمة واجهة الموسوعة الحديثية API» | JSON(P) search widget for site owners; third parties wrap it (`dorar-hadith-api`) because the official one needs jQuery/JSONP | The *idea* of an embeddable widget for other sites (§3.3) | Scraping or wrapping dorar — we only link to dorar search (referral URLs verified in STATE §3) |
| **hadeethenc.com** | Bulk download page (used by us under their redistribution terms, Q2) | — | Showing full HadeethEnc text without the owner's decision (Q2 default `link`) |

**Conclusion of the survey.** Every existing MCP/API in this space is a *retrieval* surface («give me ayah 2:255», «search hadith about …»). **None offers a deterministic *verification* primitive** («here is a text someone wrote — tell me byte-exactly where it departs from the Mushaf / the matn, without rewriting it»). That is the gap Basira fills, and it is what would make the MCP tool unique: an AI assistant can draft, then *call Basira to check its own quotes* before showing them to a user.

## 3. Design — what to add (ordered by value ÷ cost)

### 3.1 MCP server (owner's question «أفكر نضيف MCP») — **recommended, ~½ day**

* **Transport**: streamable-HTTP, mounted on the same FastAPI process at `/mcp` (python `mcp` SDK 2.2.0 is on the index; FastAPI 0.142 / Starlette 1.7 are compatible). Remote-first like quran-mcp; `stdio` optional for local IDEs.
* **Tools (read-only, deterministic, same pipeline as `/v1/check` — no second code path):**
  * `check_text(text, ui_lang="ar") → CheckResponse` — the product.
  * `check_image(image_base64, mime) → CheckResponse` — OCR then check, with `ocr_text` echoed.
  * `list_sources() → SourceInfo[]` — provenance for citations.
  * `grounding_rules() → text` — the SAFETY §1.3 red lines + the four states explained, returned once per session (hadith-mcp pattern). Key sentences: *never rewrite the quote; `not_found` means «not in our sources», not «false»; grade lines are HadeethEnc's, quoted as-is.*
* **Resources**: `basira://sources`, `basira://messages/{lang}`.
* **Guards reused**: same limiter (per client key), same 5 000-char limit, same error envelope mapped to MCP tool errors, no persistence, class-only logs.
* **Invariant tests**: tool output == `/v1/check` output for the 8 smoke cases (byte-equal JSON); forbidden-lexicon sweep over tool descriptions; a test that `grounding_rules()` text is drawn from `messages/*.json` (single source).
* **Client config to publish** (README + `/docs` page): `{"mcpServers":{"basira":{"url":"https://<host>/mcp","type":"http"}}}`.

### 3.2 API documentation page («هل صفحات API نحتاج نسوي له؟») — **yes, cheap**

`/docs` exists but is a bare Swagger UI. Minimum for «best of its kind»:
1. **`docs/API.md`** (missing today — STATE §2 item 9): quickstart with one `curl` and one `fetch` example per endpoint, the four states and their meaning, the error envelope, rate limits, the eval key, the red lines (what the API will never return).
2. Serve a human page at `/developers` (static, built by Vite) that embeds the OpenAPI reference (Scalar or Swagger UI) and the quickstart — one page, bilingual, kit design.
3. **Response examples** in the OpenAPI schema from the real fixtures in `frontend/src/__fixtures__/` (`openapi_examples` on the route) so the reference shows true data, never invented religious text.
4. Version header `X-Basira-Version` + `corpus` block already in every response → document it as the reproducibility contract.

### 3.3 Embeddable verification widget / proof links — **later (WP-10+)**

* Stateless **proof link**: `/#/check?text=<url-encoded>` re-runs the check client-side; nothing is stored (dorar/hadith-mcp «shareable link» idea without their database).
* `<script>` widget for publishers: paste-box that posts to `/v1/check` and renders the same `QuoteCard`. Needs CORS allow-list per publisher and a size budget; not before the deploy target is known.

### 3.4 Explicitly rejected

* OAuth / user accounts (nothing to protect; contradicts «لا نحفظ شيئًا»).
* Semantic/embedding search as a verification primitive (non-deterministic; I7 reproducibility).
* Serving tafsir, translations or any interpretive text (red line: never generate or curate religious text beyond the pinned corpora).
